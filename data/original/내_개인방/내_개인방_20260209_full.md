[황태욱] [오전 11:32] ### qmd 소개 및 GitHub 분석
qmd는 GitHub에서 최근 인기 있는 오픈소스 프로젝트(tobi/qmd)로, CLI 기반의 로컬 검색 엔진입니다. 개인 문서, 노트, 지식 베이스, 미팅 기록 등을 인덱싱하고 검색할 수 있게 설계되었으며, 모든 작업이 온디바이스(로컬)에서 실행되어 클라우드나 API 호출 없이 동작합니다. 주요 기능으로는:
- **하이브리드 검색 파이프라인**: BM25(키워드 기반 전체 텍스트 검색), 벡터 임베딩(의미 기반 검색), LLM 기반 재랭킹(Reciprocal Rank Fusion 사용)을 결합.
- **쿼리 확장(Query Expansion)**: 미세 조정된 LLM(qmd-query-expansion-1.7B)을 사용해 쿼리를 자동 확장하여 검색 정확도를 높임.
- **로컬 모델 통합**: GGUF 형식의 모델(EmbeddingGemma-300M, Qwen3-reranker 등)을 자동 다운로드하고 캐싱. 노드-llama-cpp로 실행.
- **통합성**: MCP 서버를 통해 AI 에이전트(예: Claude Desktop, OpenClaw)와 연동 가능. 메모리 백엔드로 사용되며, 자동 인덱싱과 임베딩 지원.
- **설치 및 사용**: Bun으로 글로벌 설치(`bun install -g github:tobi/qmd`). 컬렉션 추가, 임베딩, 검색 명령어로 간단히 운영. 최근 업데이트(2026.2.x 버전 기준)에서 OpenClaw 같은 도구와의 통합이 강화되어 메모리 효율성과 자동 주입 기능이 강조됨.
GitHub README와 리포지토리 분석 결과, qmd는 영어 중심으로 개발되었으며, 비영어 언어(특히 한국어)에 대한 명시적 지원이 없습니다. 토크나이저는 SQLite FTS5의 porter unicode61을 기본으로 사용하며, 한국어 형태소 분석이나 교착어 특성을 고려한 로직이 없음. 쿼리 확장 모델도 영어 전용(Qwen3-1.7B, language: en)으로, 임베딩 모델(EmbeddingGemma)은 한국어 최적화가 미흡. 이는 대화 내용과 일치하며, 한국어 검색 품질 저하의 원인으로 보임. 최근 이슈나 업데이트에서도 한국어 관련 언급이 없으나, 커뮤니티(예: OpenClaw 통합)에서 메모리/검색 향상을 위한 커스텀 적용 사례가 등장 중.
### 대화 내용 분석 요약
제공된 대화는 qmd의 한국어 처리 한계와 개선 방안을 중점으로 다룹니다. 핵심은 BM25 알고리즘 자체가 문제가 아니라, 입력 토크나이저의 언어 종속성 때문이라는 점. 한국어(교착어)의 특성(어간+조사/어미 결합)을 무시하면 검색 성능이 저하됨. 주요 포인트:
- **발견사항**:
- 형태소 분석기 없으면 띄어쓰기 기반(space) 토크나이제이션이 한국어 특성을 무시해 성능 저하 (예: "서울에서"와 "서울로"를 동일 취급 못 함).
- BM25가 임베딩 모델보다 우수한 경우 관찰, top-k(1~50)에서 형태소 분석기(특히 okt)가 일관되게 우월.
- 벤치마크(AutoRAG): ko_okt(F1=0.7982, 최고), ko_kkma(0.7544), ko_kiwi(0.7281), space(0.6667). okt vs space = +19.7%p 차이.
- **qmd의 현재 문제**:
- SQLite FTS5의 영어 중심 토크나이저 사용, 한국어 형태소 분석 미지원.
- 쿼리 확장과 임베딩 모델이 영어 최적화됨.
- **대안 접근법**:
- SPLADE(Naver): BERT 기반 용어 확장으로 어휘 불일치 해결.
- BM42(Qdrant): Transformer 기반 가중치, 짧은 텍스트 강점.
- Query Expansion: LLM으로 쿼리 확장, qmd의 lex:/vec:/hyde: 패턴 구현.
- 현실적 해결: 인덱싱/검색 전 형태소 분석기로 전처리(이중 파이프라인: 원문 보존 + 분석 텍스트 저장).
- **추천**: 한국어 검색에 ko_okt 권장 (NDCG, mAP 메트릭 안정). 추가로 es-hangul(자모/초성/발음 레벨, 1순위), Kiwi(kiwipiepy, 형태소 레벨, 2순위), 최적: es-hangul + Kiwi 병행.
이 분석은 "측정 도구(토크나이저)를 의심하라"는 원칙을 강조하며, qmd 적용 시 한국어 전처리가 핵심임을 지적.

## 1. qmd 깃허브 기준 현재 구조와 한국어 관점 한계
qmd는 하이브리드 검색 파이프라인이다. [github](https://github.com/tobi/qmd)
- **Lexical 검색**: SQLite FTS5(BM25) 기반 `documents_fts` 테이블
- **Vector 검색**: embeddinggemma-300M GGUF로 문서 임베딩 [github](https://github.com/tobi/qmd)
- **Re-ranking**: Qwen3-Reranker-0.6B GGUF [github](https://github.com/tobi/qmd)
- **Query Expansion**: Qwen3-1.7B 기반 `qmd-query-expansion-1.7B` 모델이 `lex:/vec:/hyde:` 포맷으로 확장 쿼리를 생성해 BM25와 vector 둘 다에 넣어줌 [huggingface](https://huggingface.co/tobil/qmd-query-expansion-1.7B)
문제는:
1. **FTS5 토크나이저**
- qmd는 SQLite FTS5의 `porter unicode61` 토크나이저를 사용한다는 분석이 있었고, FTS5 기본 토크나이저(unicode61)는 공백과 구두점을 기준으로 토큰을 나누는 영어 중심 설계다. [sqlite](https://www.sqlite.org/fts5.html)
- 한국어에서는 `"인증은"`이 하나의 어절로 들어가면, `"인증"`으로는 매칭이 안 되는 문제가 실제로 지적된다. [javaexpert.tistory](https://javaexpert.tistory.com/1589)
- StackOverflow/공식 문서에서도 CJK(중국어/일본어/한국어)에 대해 unicode61이 제대로 동작하지 않는다는 보고가 있다. [stackoverflow](https://stackoverflow.com/questions/52422437/why-sqlite-fts5-unicode61-tokenizer-does-not-support-cjkchinese-japanese-korean)
2. **Query Expansion 모델**
- `qmd-query-expansion-1.7B`는 입력 쿼리를 받아서
- `hyde:` 1개 (가상의 답변 문단)
- `lex:` 3개 (BM25용 키워드 문구)
- `vec:` 3개 (벡터용 자연어 문장)
를 생성하는 전용 모델이다. [huggingface](https://huggingface.co/tobil/qmd-query-expansion-1.7B-gguf)
- 하지만 이 모델은 **영어 쿼리만으로 학습되었고**, 한계 항목에도 “Trained on English queries only”라고 명시돼 있다. [huggingface](https://huggingface.co/tobil/qmd-query-expansion-1.7B/resolve/main/README.md?download=true)
3. **임베딩 모델**
- 기본 임베딩은 `embeddinggemma-300M`으로, 멀티링구얼이긴 하지만 한국어에 최적화된 한국어 전용 임베딩(upstage, jina-korean, bge-ko 등)에 비하면 성능이 떨어지는 편이다. [github](https://github.com/tobi/qmd)
- AutoRAG 벤치마크에서도 특정 한국어 데이터셋에서 BM25가 한국어 임베딩(upstage_embed)보다 mAP/NDCG가 더 좋은 경우가 보고되어 있다. [velog](https://velog.io/@autorag/%ED%95%9C%EA%B5%AD%EC%96%B4-BM25%EC%97%90%EC%84%9C-%EC%B5%9C%EA%B3%A0%EC%9D%98-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80%EB%8A%94-%EB%AC%B4%EC%97%87%EC%9D%B8%EA%B0%80-%ED%95%9C%EA%B5%AD%EC%96%B4-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80-%EB%B2%A4%EC%B9%98%EB%A7%88%ED%81%AC-%EA%B0%80%EB%B3%B4%EC%9E%90%EA%B3%A0)
이걸 합치면:
> qmd의 설계 자체(하이브리드, query expansion, rerank)는 훌륭한데, **그 앞단 토크나이저/모델이 영어 기준이라 한국어에서 제 성능이 안 나온다**는 상황이다.
## 2. AutoRAG 벤치마크 정리: 왜 형태소 분석기가 이렇게 중요한가
AutoRAG의 한국어 BM25 토크나이저 벤치마크 결과 요약: [marker-inc-korea.github](https://marker-inc-korea.github.io/AutoRAG/nodes/retrieval/bm25.html)
| 토크나이저 | 특성 | F1 (top‑k=1) |
|-----------|------|--------------|
| **ko_okt** | KoNLPy OKT 형태소 분석기 | **0.7982** |
| ko_kkma  | 서울대 KKMA, 정확하지만 느림 | 0.7544 |
| ko_kiwi  | C++ Kiwi, 빠르고 안정적 | 0.7281 |
| space    | 그냥 띄어쓰기 기반 | 0.6667 |
- OKT vs space = **+19.7%p** 차이.
→ **형태소 분석기만 교체해도 BM25 품질이 크게 오른다.** [velog](https://velog.io/@autorag/%ED%95%9C%EA%B5%AD%EC%96%B4-BM25%EC%97%90%EC%84%9C-%EC%B5%9C%EA%B3%A0%EC%9D%98-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80%EB%8A%94-%EB%AC%B4%EC%97%87%EC%9D%B8%EA%B0%80-%ED%95%9C%EA%B5%AD%EC%96%B4-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80-%EB%B2%A4%EC%B9%98%EB%A7%88%ED%81%AC-%EA%B0%80%EB%B3%B4%EC%9E%90%EA%B3%A0)
- 같은 실험에서 한국어 임베딩 모델(upstage_embed)이 rank‑aware metric(mAP, NDCG)에서 BM25보다 성능이 떨어지는 경우도 관찰됨. [velog](https://velog.io/@autorag/%ED%95%9C%EA%B5%AD%EC%96%B4-BM25%EC%97%90%EC%84%9C-%EC%B5%9C%EA%B3%A0%EC%9D%98-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80%EB%8A%94-%EB%AC%B4%EC%97%87%EC%9D%B8%EA%B0%80-%ED%95%9C%EA%B5%AD%EC%96%B4-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80-%EB%B2%A4%EC%B9%98%EB%A7%88%ED%81%AC-%EA%B0%80%EB%B3%B4%EC%9E%90%EA%B3%A0)
- 결론:
- 한국어에서는 “BM25 vs 벡터” 이전에 **“어떤 토크나이저를 쓰느냐”**가 더 크다.
- 벡터 서치보다 **형태소+BM25 조합이 더 낫게 나오는 경우가 충분히 있다.**
당신이 요약한 “BM25 알고리즘은 언어 중립적이지만, 토크나이저는 언어 종속이다”라는 해석이 AutoRAG 결과와 정확히 일치한다.
## 3. qmd에서 한국어 검색 품질을 올리는 전체 전략
정리하면 전략은 이렇다:
1. **Lexical 레이어**
- FTS5 자체는 그대로 두고, **인덱싱/쿼리 양쪽에서 한국어 형태소 분석을 선행**한다.
- “교착어 → 형태소 단위로 잘라서 공백으로 구분된 토큰 시퀀스”로 변환한 후 FTS5에 넣는다.
2. **Vector 레이어**
- 원문을 그대로 둬서 벡터 임베딩용으로 사용.
- 한국어 전용 임베딩으로 갈아끼우거나, vector 가중치를 보조 정도로 쓰는 방향.
3. **Query Expansion 레이어**
- 영어 전용 query expansion은 한국어에선 오히려 노이즈가 될 수 있으므로:
- (단기) 한국어 쿼리는 expansion을 끄거나 제한한다.
- (중기) 한국어용 lex/vec/hyde 모델로 교체한다.
4. **es-hangul**
- 형태소 단위 위에 **자모/초성 레벨 토큰을 추가로 얹어서** 초성 검색, 철자 변형, 발음 기반 검색을 보강.
아래부터는 “실제로 qmd + Claude Code 환경에서 당장 적용 가능한 것” 기준으로 단계별 추천을 정리한다.
## 4. 1단계: 코드 수정 없이 바로 할 수 있는 운영 팁
### 4.1 검색 명령 선택 전략
- **한국어 위주의 쿼리면**
- `qmd query`(하이브리드 + query expansion)보다는
- `qmd search` (BM25 only)
- 필요시 `qmd vsearch` (벡터)
를 **분리해서 쓰는 것**을 추천.
- 이유:
- query expansion 모델이 영어 전용이라, 한국어 입력 시
- 쓸모없는 영어 lex/vec 라인을 뿌리거나 [huggingface](https://huggingface.co/tobil/qmd-query-expansion-1.7B)
- BM25 ranking을 희석시킬 수 있다.
- `search`는 FTS5 BM25만 쓰므로 “토크나이저만 잘 다듬으면 가장 믿을 만한 축”이 된다.
### 4.2 쿼리 작성 습관
토크나이저를 바꾸기 전까지는, 사용자 쿼리 쪽에서 이를 보정할 수 있다:
- **조사/어미 제거**:
- `"서울에서 맛집 추천해줘"` → `"서울 맛집 추천"`
- **핵심 명사+동사 위주**로 짧게:
- `"인증 토큰 만료 문제 디버깅 방법"` → `"인증 토큰 만료 디버깅"`
- Claude Code 프롬프트에:
- “내 한국어 질문을 BM25 친화적인 키워드 쿼리(명사/동사, 조사 제거)로 바꾼 다음 qmd search를 호출해줘”
- 같은 규칙을 넣어 두면, 에이전트가 자동으로 “형태소 분석 흉내”를 내 줄 수 있다.
이건 근본 해결은 아니지만, **당장 체감 품질을 올릴 수 있는 가장 쉬운 조치**다.
## 5. 2단계: qmd를 그대로 두고, “이중 파이프라인 + 형태소 전처리” 붙이기
대화 내용에도 나왔듯이, 가장 현실적인 해결책은:
> 원문은 벡터용으로 그대로 두고, **형태소 분석된 텍스트를 따로 만들어서 BM25 인덱스에 넣는 이중 파이프라인**이다.
qmd를 크게 뜯지 않고 할 수 있는 버전부터 보자.
### 5.1 별도 “형태소 토큰 전용 컬렉션” 만들기 (qmd 포크 없이)
1. **형태소 분석기 선택**
- 정확도 우선: `ko_okt` (konlpy) – 성능 최고지만 Java 의존성, 속도 부담 [marker-inc-korea.github](https://marker-inc-korea.github.io/AutoRAG/nodes/retrieval/bm25.html)
- 실용적인 타협: **Kiwi(kiwipiepy)** – C++ 기반, 빠르고 파이썬만으로 설치 가능 [github](https://github.com/bab2min/kiwipiepy)
- 속도/배포까지 고려하면, CLI/스크립트용으로는 Kiwi 추천.
2. **전처리 스크립트 작성 (Python)**
- 입력: 기존 마크다운 파일
- 과정:
- 전체 텍스트를 Kiwi/OKT로 토크나이즈
- 어간/표제어(lemma) 위주로 추출 (불필요한 조사/어미/기호 제거)
- `서울에서`, `서울로` → `서울` 같은 형태로 정규화
- 출력: “형태소 토큰만 공백으로 나열한 버전”의 `.md` 파일
- 예: `my_note.md` → `my_note.ko_tokens.md`
내용은 `서울 여행 코스 추천 음식 맛집 …`처럼 키워드 덤핑
3. **새로운 qmd 컬렉션 추가**
- 예)
- 원본: `~/notes` → `qmd collection add ~/notes --name notes`
- 토큰용: `~/notes_ko_tokens` → `qmd collection add ~/notes_ko_tokens --name notes-ko-lex`
- 이렇게 하면:
- 벡터/컨텍스트: `notes`
- BM25(한국어 친화): `notes-ko-lex`
4. **검색시 사용 패턴**
- Claude MCP / CLI에서:
- 정밀 키워드 검색: `qmd search "서울 여행" -c notes-ko-lex`
- 의미 검색 + 전체 문맥: `qmd vsearch "서울 여행" -c notes`
- 필요하면 두 결과를 에이전트에서 병합 (랭크퓨전/교집합 등)
장점:
- qmd 코어를 안 건드려도 되고, 스크립트만 유지하면 된다.
- AutoRAG에서 본 것처럼, 형태소 분석 결과만 잘 만들어줘도 BM25 성능이 확 뛰는 구조를 따라갈 수 있다. [velog](https://velog.io/@autorag/%ED%95%9C%EA%B5%AD%EC%96%B4-BM25%EC%97%90%EC%84%9C-%EC%B5%9C%EA%B3%A0%EC%9D%98-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80%EB%8A%94-%EB%AC%B4%EC%97%87%EC%9D%B8%EA%B0%80-%ED%95%9C%EA%B5%AD%EC%96%B4-%ED%86%A0%ED%81%AC%EB%82%98%EC%9D%B4%EC%A0%80-%EB%B2%A4%EC%B9%98%EB%A7%88%ED%81%AC-%EA%B0%80%EB%B3%B4%EC%9E%90%EA%B3%A0)
단점:
- 인덱스가 2세트라서 저장공간/업데이트 관리가 조금 번거로움.
## 6. 3단계: qmd 포크해서 FTS 파이프라인에 형태소 + es-hangul 직접 통합
조금 더 “정석적인” 방향은 qmd를 포크해서 DB/인덱싱 로직을 고치는 것이다.
### 6.1 인덱싱 파이프라인 변경(고수준 설계)
대략적인 구조는:
1. `documents` 테이블에 원본 마크다운 저장 (지금과 동일) [github](https://github.com/tobi/qmd)
2. 문서 저장/갱신 시:
- JS/Bun에서 **Python (Kiwi) 또는 Node 기반 형태소 분석기**를 호출
- 결과를 `analyzed_text` 같은 컬럼에 저장
3. FTS5 테이블을 `analyzed_text` 기준으로 구성
- `CREATE VIRTUAL TABLE documents_fts USING fts5(analyzed_text, tokenize='porter unicode61', content='documents', content_rowid='rowid');`
- 혹은 contentless 모드 + 트리거
즉, FTS5에 들어가는 텍스트 자체를 “형태소 토큰 시퀀스”로 만들어 버리는 방식이다.
### 6.2 es-hangul을 얹어서 “자모/초성 검색”까지 지원
`toss/es-hangul`은 다음을 지원한다: [github](https://github.com/toss/es-hangul)
- 초성/중성/종성 분해
- 초성 검색 (예: `"라면"` ↔ `"ㄹㅁ"`)
- 발음/유사도 계산 등
이걸 BM25에 얹는 방법은:
1. 형태소 결과(예: `라면`, `맛집`)에 대해
- `getChoseong("라면")` → `ㄹㅁ` 같은 초성 시퀀스를 생성 [github](https://github.com/toss/es-hangul)
2. `analyzed_text`에 추가 토큰으로 함께 적재
- 예: `라면 맛집` → `라면 맛집 ㄹㅁ ㅁㅈ`
3. 쿼리 측에서도:
- 사용자가 `ㄹㅁ`만 입력해도 해당 토큰이 걸리게 됨.
- 쿼리 전처리 단계에서, 한글 입력이지만 초성 패턴처럼 보이면(es-hangul로 판별) 그대로 사용.
대화에서 나온 추천처럼 정리하면:
- **1순위**: es-hangul – 한글 자모/초성/발음 레벨 처리 (Bun 네이티브, 의존성 적음) [github](https://github.com/toss/es-hangul)
- **2순위**: Kiwi(kiwipiepy) – 형태소/어간/조사 레벨 [bab2min.github](https://bab2min.github.io/kiwipiepy/v0.15.1/kr/)
- **최적 조합**: Kiwi로 형태소 단위, es-hangul로 자모 단위를 같이 인덱싱
→ 교착어/철자 변형/초성 검색까지 한 번에 커버
이 조합은 “교착어(BM25) + 한글 특유의 초성 검색 UX”를 동시에 잡는 구조라, Obsidian/노트 검색용으로는 체감이 꽤 클 것이다.
## 7. 4단계: Query Expansion/모델 쪽 한국어화
형태소/토크나이저 레이어를 정리했다면, 다음 단계는 **쿼리 확장/벡터 모델 쪽 한국어 최적화**다.
### 7.1 Query Expansion 모델 교체/차단
현재 `qmd-query-expansion-1.7B`는 다음 특징을 가진다: [huggingface](https://huggingface.co/tobil/qmd-query-expansion-1.7B-gguf)
- `lex:`, `vec:`, `hyde:` 라인 기반 출력
- BM25와 벡터를 동시에 강화하는 구조
- **영어 쿼리만**으로 학습됨(한계 항목에 명시) [huggingface](https://huggingface.co/tobil/qmd-query-expansion-1.7B/resolve/main/README.md?download=true)
추천:
- **단기**
- qmd를 그대로 쓴다면, 한글 쿼리에 대해서는:
- `qmd query` 대신 `search`+`vsearch`를 직접 쓰고,
- Agent 레벨에서 두 결과를 RRF나 간단 가중 평균으로 병합.
- 또는 qmd 코드에서 “쿼리에 한글 포함 시 query expansion 스킵” 룰 추가.
- **중기**
- 같은 lex/vec/hyde 포맷으로 **한국어 전용 query expansion LLM**을 하나 fine-tuning:
- 베이스: ko-llama, Solar, Ko-Gemma, Qwen-한국어 LoRA 등
- 데이터: 자주 쓰는 업무 도메인 쿼리 → 적절한 lex/vec/hyde 라인
- qmd의 DEFAULT_GENERATE_MODEL을 이 한국어 모델로 바꿔치기.
이렇게 하면 AutoRAG에서 권장하는 “쿼리 확장 + BM25/Vector 동시 전달” 패턴을 **한국어 데이터에도 제대로 적용**할 수 있다. [gbdai.tistory](https://gbdai.tistory.com/75)
### 7.2 임베딩 모델 교체
- embeddinggemma-300M 대신:
- 한국어 성능 검증된 임베딩 (예: Ko-bge, upstage-ko, jina-ko 등)을 GGUF로 변환해서 node-llama-cpp에서 쓰도록 설정.
- AutoRAG 결과처럼, 한국어에서는 BM25+형태소가 여전히 강하므로:
- “BM25 = 주력, 벡터 = recall 보조 + rerank 재료” 정도로 생각하고 가중치를 조절하는 게 현실적이다. [youtube](https://www.youtube.com/watch?v=ckHAvm-L6Sc)
## 8. 우선순위/로드맵 요약
실제 구현 난이도와 효과 기준으로 정리하면:
1. **오늘 바로**
- 한국어 쿼리 → `qmd search` 위주 사용 (하이브리드 `query`는 가급적 영어/혼합쿼리에서만)
- 쿼리에서 조사/어미 제거, 핵심 명사/동사 위주로 쓰기
- Claude Code/에이전트에게 “BM25 친화 키워드 쿼리로 리라이팅 후 qmd 호출” 역할 맡기기

- `kiwipiepy`나 `konlpy`(OKT)로 마크다운을 형태소 토큰 시퀀스로 바꾸는 Python 스크립트 작성

- 검색 시 `-c notes-ko-lex`로 BM25, 원본 컬렉션으로 벡터/문맥 같이 조회
3. **장기/프로덕션**
- qmd 포크해서:
- 인덱싱 시 한국어 형태소 분석(kiwi/OKT) + es-hangul로 초성 토큰 생성
- FTS5는 이 전처리된 텍스트로 인덱싱
- 원문은 벡터/표시용으로 유지
- query expansion/임베딩 모델을 한국어 친화 모델로 교체
- AutoRAG 같은 도구를 이용해, 실제 본인 데이터셋에 대해 BM25/임베딩 조합을 벤치마크해 최적 k, 가중치 세팅 찾기 [marker-inc-korea.github](https://marker-inc-korea.github.io/AutoRAG/nodes/retrieval/bm25.html)
요약하면, 이 리서치에서 얻은 인사이트를 qmd에 적용하려면:
- **“먼저 토크나이저를 의심하라”**는 원칙대로,
- FTS5 내부를 바꾸기보다는 **앞단 한국어 형태소/자모 전처리**를 붙이고,
- query expansion/벡터는 “영어 전용”이라는 가정하에 한국어 전용으로 천천히 교체해 가는 것이 가장 현실적인 로드맵이다.

## 1) qmd 구조 요약: 어디를 건드려야 성능이 오르는가
qmd는 로컬에서 **BM25(=SQLite FTS5) + Vector Search(sqlite-vec) + LLM Re-ranking**을 결합하는 하이브리드 검색 파이프라인입니다. ([GitHub][1])
특히 `qmd query`는 **Query Expansion → (FTS+Vector 병렬) → RRF Fusion(k=60) + top-rank bonus → 상위 30 rerank → position-aware blend**로 설계돼 있습니다. ([GitHub][1])
중요한 건, qmd의 BM25는 **FTS5 토크나이저가 `porter unicode61`**로 고정돼 있다는 점입니다. ([GitHub][2])
즉 “BM25가 한국어에 약하다”가 아니라 **“BM25 앞단 토큰화가 한국어에 부적합”**이라는 지금 대화의 결론이 qmd에도 그대로 적용됩니다.
## 2) 지금 대화(“OKT가 space 대비 압도”)와 qmd를 연결하면 나오는 결론
### (A) 한국어에서 BM25 성능의 1차 병목 = 토큰화
* qmd 기본 FTS 토큰화가 한국어 형태소/어간/조사 처리를 하지 못하니, “서울에서/서울로” 같은 변형이 **서로 다른 토큰**으로 남습니다. ([GitHub][2])
* 그래서 AutoRAG 벤치마크에서 관찰한 것처럼, **형태소 분석기(OKT/Kiwi 등)만 넣어도 BM25가 크게 튑니다**(당신이 공유한 표/수치와 정합).
### (B) qmd의 Query Expansion은 “형식은 좋지만, 언어가 문제”
qmd는 쿼리 확장을 위해 **qmd-query-expansion-1.7B(=Qwen3-1.7B 파인튜닝)**을 사용합니다. ([GitHub][1])
그런데 해당 모델 카드에 **language: en**으로 명시돼 있어 한국어 코퍼스에서는 확장이 “도움”이 아니라 “노이즈”가 될 가능성이 큽니다. ([Hugging Face][3])
(qmd는 원쿼리 가중치×2 + top-rank bonus로 방어하지만, 확장 쿼리가 한국어 문서에 안 맞으면 RRF 단계에서 후보가 흔들릴 수 있습니다. ([GitHub][1]))
### (C) Vector / Rerank도 “기본값은 범용/영어 중심”
qmd 기본 모델은 `embeddinggemma-300M`, `qwen3-reranker-0.6b`, `qmd-query-expansion-1.7B` 3종입니다. ([GitHub][1])
한국어 성능을 올리려면 **토큰화(FTS) + (가능하면) 한국어/다국어 임베딩 + 다국어 reranker + 한국어 QE** 순으로 손보는 게 가장 효율적입니다.
## 3) 추천사항: “바로 적용” → “제대로 고치기” 우선순위
### 1순위 (가장 현실적/효과 큼): **FTS 전처리로 ‘형태소 토큰’을 FTS에 넣기**
qmd의 FTS5 자체를 바꾸지 않아도, **인덱싱 시점에 본문을 형태소 토큰(공백 분리)으로 변환**해서 `documents_fts.body`에 저장하면 BM25가 즉시 개선됩니다. ([GitHub][1])
* 당신이 정리한 “이중 파이프라인(원문=임베딩용, 형태소 텍스트=FTS용)”이 qmd 스키마/구조와 정합입니다. ([GitHub][1])

* 도메인 문서(회의록/기술문서)면 **영문 토큰/코드 토큰은 그대로 보존**(porter가 영어에만 의미 있게 작동) ([GitHub][2])
### 2순위 (한국어 UX 체감 크게 개선): **es-hangul(자모/초성) 토큰을 ‘보조 채널’로 병행**
토스의 `es-hangul`은 초/중/종성 분해, 초성 검색 등 **한글 문자열 처리**에 특화된 JS 라이브러리입니다. ([GitHub][5])
이걸 FTS 토큰에 **보조로 섞으면** 다음이 개선됩니다.
* 띄어쓰기 흔들림, 오타, 초성만 입력(“ㄷㅇㅌ”, “ㅈㅅ”) 같은 케이스
* 형태소 분석이 놓치는 **부분 매칭/자모 레벨** 탐색
권장 조합은 당신이 적은 그대로 **“Kiwi(형태소) + es-hangul(자모/초성)”**이 맞습니다.
### 3순위 (하이브리드의 ‘dense’ 축을 한국어로 정상화): 임베딩/리랭커 교체
qmd는 GGUF를 node-llama-cpp로 돌립니다. ([GitHub][1])
한국어에선 아래 옵션이 현실적입니다.
* **임베딩(추천)**

* `multilingual-e5-*` GGUF: 다국어 검색 임베딩 계열(GGUF 배포 존재) ([Hugging Face][7])
* `jina-embeddings-v3` GGUF: 다국어 임베딩 GGUF 배포 존재 ([Hugging Face][8])
* **리랭커(추천)**
* `bge-reranker-v2-m3` GGUF: “multilingual reranker”로 문서화/배포 ([BGE Model][9])
### 4순위 (qmd query 품질을 ‘한국어’로 완성): **한국어 Query Expansion 모델**
현재 qmd-query-expansion은 “형식(lex/vec/hyde) 자체는 매우 좋지만”, 언어가 `en`입니다. ([Hugging Face][3])
따라서 한국어 코퍼스라면:
* **단기**: 한국어 질의에 대해선 QE를 줄이거나(혹은 원쿼리만) 쓰는 편이 낫고
* **중장기**: 동일 템플릿(hyde/lex/vec)으로 **한국어 데이터로 파인튜닝한 QE 모델**을 별도로 두는 게 정석입니다. (qmd도 finetune 디렉토리를 제공) ([GitHub][10])

## 5) “랩장님 보고”용 결론(핵심만)
* qmd의 BM25는 문제가 아니라 **FTS 토큰화가 한국어에 부적합**(porter unicode61)인 게 병목 ([GitHub][2])
* 해결 1순위: **인덱싱/검색 양쪽에서 형태소 전처리(=토큰을 공백 분리) 후 FTS에 저장** → BM25 품질 급상승(OKT/Kiwi 효과와 동일 논리) ([GitHub][1])
* 해결 2순위: **es-hangul(자모/초성) 보조 토큰**을 섞어 한국어 UX(오타/초성검색) 강화 ([GitHub][5])
* 해결 3순위: 임베딩/리랭커를 한국어/다국어 모델(GGUF)로 교체(KURE, multilingual-e5, bge-reranker-v2-m3 등) ([Hugging Face][6])
* 해결 4순위: qmd-query-expansion은 `language: en`이라 한국어 코퍼스에선 **한국어 QE 모델이 별도로 필요** ([Hugging Face][3])
```bash
# (A) Claude Code / MCP 연동 (README 그대로)
# ~/.claude/settings.json
{
"mcpServers": {
"qmd": { "command": "qmd", "args": ["mcp"] }
}
# (B) “qmd를 안 고치고도” BM25(FTS)만 한국어 토큰화 효과를 보는 가장 쉬운 방법:
# 1) 원본 마크다운을 “형태소 토큰 공백분리 버전”으로 미러(shadow) 디렉토리에 생성
# 2) 그 미러를 qmd 컬렉션으로 추가해서 BM25 search를 그쪽에 걸기
# 3) 결과 경로를 원본 경로로 매핑해서 qmd get
# 0) deps
pip install kiwipiepy
# 1) shadow 생성 스크립트 (최소형)
cat > build_kofts.py << 'PY'
import os, sys, pathlib
from kiwipiepy import Kiwi
src = pathlib.Path(sys.argv[1]).expanduser().resolve()
dst = pathlib.Path(sys.argv[2]).expanduser().resolve()
kiwi = Kiwi()
def tok(s: str) -> str:
# 형태소 토큰(표면형)만 공백으로 연결 (필요하면 품사 필터링/정규화 추가)
return " ".join([t.form for t in kiwi.tokenize(s)])
for p in src.rglob("*.md"):
rel = p.relative_to(src)
out = dst / rel
out.parent.mkdir(parents=True, exist_ok=True)
txt = p.read_text(encoding="utf-8", errors="ignore")
out.write_text(tok(txt), encoding="utf-8")
PY
# 2) shadow 빌드
python build_kofts.py ~/notes ~/notes_kofts
# 3) qmd에 shadow 컬렉션 추가 (BM25용)
qmd collection add ~/notes_kofts --name notes_kofts
# 4) 한국어 키워드 검색(BM25)을 shadow에 걸고, 결과 파일명을 원본에서 열기(간단 운영 예시)
qmd search "서울에서 회의록" -c notes_kofts --files -n 10
# (C) “제대로 고치기”(fork 권장): qmd 인덱싱 시 documents_fts.body에 tokenized 텍스트를 넣고,
# 검색 시에도 FTS query만 동일 전처리 적용.
# - 토큰화: Kiwi(형태소) + es-hangul(초성/자모 보조) 병행 권장
# - 모델: 임베딩(KURE/multilingual-e5/jina-v3), 리랭커(bge-reranker-v2-m3), QE(한국어 파인튜닝)
```

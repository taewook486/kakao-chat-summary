# qmd는 肺(폐)의 진화다

15 ## 아이디어
16
17 十一臟腑에서 肺(폐)는 LanceDB/Qdrant 벡터 스토어를 가리킨다. qmd(Query Markup Documents)는 이 폐를 **하이브리드 검색 엔진*
*으로 진화시킨 것이다:
18
19 - **BM25 (키워드)**: 정확한 용어 매칭 — 빠르고 예측 가능
20 - **벡터 검색**: 의미적 유사성 — "같은 뜻의 다른 표현"을 찾음
21 - **LLM 리랭킹**: 맥락을 이해하여 결과 품질 극대화
22
23 폐가 공기(정보)를 걸러 산소(지식)만 혈류에 보내듯, qmd는 1,000+ 문서에서 핵심 청크만 추출하여 LLM 컨텍스트에 주입한다.

1.1. AI 모델: 생각하고 판단하는 '두뇌'
AI 모델의 정의 및 역할
AI 모델은 사람의 언어를 이해하고 답변을 생성하는 인공지능 프로그램이며, 쉽게 말해 두뇌 역할을 한다.
수십억 개의 텍스트 데이터(책, 웹사이트, 논문, 코드 등)를 학습하여 언어의 패턴과 맥락을 이해하는 방법을 터득한다.
한계: AI 모델은 대화만 할 수 있으며, 직접 파일을 만들거나 코드를 실행하거나 폴더를 정리하는 등의 행동은 못 한다.
예시: "바탕 화면에 새 폴더를 만들어 줘"라고 요청하면, AI 모델은 "우클릭하고 새 폴더를 선택하면 됩니다"와 같이 방법만 알려준다.
대표적인 AI 모델별 특징
AI 모델은 만드는 회사마다 훈련 데이터와 중점이 달라 같은 질문에도 다른 스타일로 답변한다.
클로드(Claude): 엔트로픽이 개발했으며, AI에게 원칙을 가르쳐 스스로 판단하게 훈련하여 코딩 정확도가 높고 신중한 답변이 특징이다.
GPT: 오픈 AI가 개발했으며, 사람들의 피드백을 대량으로 반영하여 선호하는 답변을 학습하여 범용적이고 유연한 답변에 강하다.
제미나이(Gemini): 구글이 개발했으며, 처음부터 텍스트, 이미지, 영상을 동시에 이해하도록 설계되어 멀티미디어를 이해하는 데 특히 강하다.
1.2. AI 코딩 도구: 실제 행동을 수행하는 '손과 발'
AI 코딩 도구의 정의 및 역할
AI 코딩 도구는 AI 모델에 실제 행동 능력을 부여하는 소프트웨어이며, AI 모델이 두뇌라면 코딩 도구는 손과 발이다.
AI 모델만 사용하면 코드를 채팅창에 텍스트로 보여주므로 사용자가 직접 복사, 붙여넣기, 실행, 에러 문의 등을 해야 한다.
AI 코딩 도구를 사용하면 프로젝트 구조를 스스로 파악하고, 필요한 파일을 직접 만들고, 코드를 작성한 뒤 완료를 알려준다.
AI 코딩 도구의 세 가지 유형
터미널 기반 도구:
목표만 말하면 프로젝트 전체를 분석하고 자율적으로 작업한다.
대표적인 예시: 엔트로픽의 클로드 코드(Claude Code), 구글의 제미나이 CLI(Gemini CLI).
데스크톱 IDE 기반 도구:
코드 편집기 안에서 AI의 도움을 받는 방식이다.
대표적인 예시: 커서(Cursor), 윈드서프(Windsurf), 안티그래비티(Antigravity).
웹 IDE 기반 도구:
설치 없이 브라우저만 열면 바로 코딩을 시작할 수 있다.
대표적인 예시: 레플릿(Replit), 볼트 러버블(Volt Rubble).
초보자나 빠른 프로토타이핑에 적합하지만, 복잡한 프로젝트에는 한계가 있다.
1.3. 도구 선택 기준 및 같은 모델 사용 시 결과 차이
상황에 따른 도구 선택 기준
웹 IDE: 설치 없이 브라우저로 간단한 웹 페이지를 제작하고 싶을 때 적합하다.
데스크톱 IDE: 코드를 직접 보면서 수정하고 싶고 복잡한 프로젝트를 수행하고 싶을 때 적합하다.
터미널 기반 도구: 큰 프로젝트를 AI의 강력한 퍼포먼스로 진행하고 싶을 때 가장 강력하다.
터미널 기반은 복잡한 결과물을 만들어내는 능력이 강력하며, 코드 편집기 내장 터미널에서 실행하여 디렉터리 확인 및 간단한 수정의 편리함과 강력한 퍼포먼스를 동시에 얻을 수 있다.
같은 AI 모델이라도 결과가 다른 이유
여러 AI 코딩 도구에서 같은 클로드 모델을 사용하더라도, 최종 결과(경험)는 완전히 달라질 수 있다.
원인: 각 도구가 AI를 활용하는 방식이 다르기 때문이다.
시스템 프롬프트: AI에게 주는 기본 지시가 다르다.
에이전트 루프: AI가 일하는 방식이 다르다.
컨텍스트 관리: AI가 기억하는 방식이 다르다.
전용 기능: 스킬, 메모리, 서브 에이전트 같은 전용 기능들이 도구별로 다르다.
비유: AI 모델은 엔진이고 AI 코딩 도구는 차종이다. 같은 엔진이라도 차종에 따라 경험과 용도가 완전히 다르다.
2. AI 코딩 트렌드 변화와 클로드 코드의 차별점
ai 모델 성능 향상으로 개발 트렌드가 코드 편집기 기반에서 터미널 기반의 자율주행 방식으로 전환되고 있으며, 클로드 코드는 컨텍스트 엔지니어링과 네이티브 통합으로 최적의 결과를 제공한다.
2.1. 개발 패러다임의 변화: 코드 편집기 기반에서 터미널 기반으로
코드 편집기 기반(IDE)의 특징
열린 파일을 중심으로 빠르게 응답하며, 코드를 작성하다 막히면 자동 완성이나 코드 조각을 즉시 제안한다.
비유: 개발자가 직접 운전하며 막히는 곳에서만 도움을 받는 내비게이션과 같다.
과거에는 AI 생성 코드 품질이 낮아 개발자가 직접 타이핑하며 AI 도움을 받는 방식이 현실적이었기 때문에 커서, 윈드서프 같은 코드 편집기 기반 도구가 인기를 끌었다.
터미널 기반의 특징 및 트렌드 전환
터미널 기반은 프로젝트 전체를 분석한 뒤 작업을 수행한다.
비유: 목적지만 말하면 AI가 알아서 데려다주는 자율주행과 같다.
예시: "로그인 기능을 만들어 줘"라고 목표만 말하면 AI가 프로젝트 구조를 파악하고 필요한 파일을 찾아 작업한다.
트렌드 변화: 2024년 현재 AI 모델의 성능이 비약적으로 향상되어 AI가 생성하는 코드 품질이 충분히 높아졌다.
이제 개발자가 한 줄 한 줄 직접 타이핑할 필요가 줄어들었으며, 개발자의 역할이 타이핑에서 의사 결정으로, 실행자에서 설계자로 바뀌고 있다.
클로드 코드는 이러한 터미널 기반 자율주행 방식의 대표 주자이다.
2.2. 클로드 코드의 차별점 1: 컨텍스트 엔지니어링 최적화
컨텍스트 엔지니어링의 중요성 부각
과거에는 프롬프트 엔지니어링(어떻게 말할지, 예: "단계별로 생각해 줘")이 중요했지만, 이제는 컨텍스트 엔지니어링(AI가 무엇을 알고 있는지)이 더 중요하다.
쇼피파이 CEO는 AI 시대의 핵심 역량이 컨텍스트 엔지니어링이라고 강조했다.
컨텍스트 엔지니어링이란 LLM이 작업을 해결할 수 있도록 모든 맥락을 제공하는 기술을 의미한다.
컨텍스트 관리 실패의 문제점
랭체인 보고서에 따르면, AI 에이전트 운영 조직의 57%가 품질 문제를 겪고 있으며, 대부분의 실패 원인은 AI 모델 능력 부족이 아닌 컨텍스트 관리 실패에서 비롯된다.
AI 에이전트가 API 호출, 파일 읽기, 로그 분석 과정에서 불필요한 정보가 계속 쌓이면, 이 정보가 초기 지시 사항을 묻어버려 AI가 방향을 잃게 된다.
아무리 똑똑한 AI 모델이라도 무엇을 해야 하는지 기억하지 못하면 제대로 된 결과를 낼 수 없다.
클로드 코드의 컨텍스트 엔지니어링 도구
클로드 코드는 컨텍스트 엔지니어링을 위한 강력한 도구들을 제공하며, 핵심은 필요한 정보만 정확하게 제공하는 것이다.
클로드.md 파일: 프로젝트 규칙을 미리 알려주어 매번 설명할 필요가 없다.
에이전트 스킬 기술: 필요할 때만 전문 지식을 활성화한다.
MCP 툴서치: 필요한 도구만 찾아서 사용하여 컨텍스트 윈도우의 토큰을 효과적으로 절감한다.
후기(Hook)나 서브 에이전트 기술: 모든 대화에서 필요한 맥락(정보)만 넣어준다.
클로드 코드를 사용하는 것만으로도 필요한 정보만 필요할 때 전달하는 컨텍스트 엔지니어링이 가능해진다.
2.3. 클로드 코드의 차별점 2: 네이티브 통합 및 활용성
네이티브 통합의 이점
클로드 코드는 클로드를 만든 엔트로픽이 직접 개발한 AI 코딩 도구이다.
커서, 윈드서프 등 다른 도구들은 공개된 API 문서만 보고 클로드를 외부로 호출하는 방식이다.
클로드 코드는 모델을 직접 만들었기 때문에, 어떤 프롬프트에 잘 반응하는지, 어떤 컨텍스트 구조가 효과적인지, 토큰 배치를 어떻게 해야 최적의 결과가 나오는지 정확히 알고 있다.
비유: 다른 도구들이 자동차 매뉴얼만 보고 운전하는 것이라면, 클로드 코드는 자동차를 직접 설계한 엔지니어가 운전하는 것과 같아 성능을 끌어내는 수준이 다르다.
성능 및 활용의 강점
비교 분석 결과, 클로드 코드는 동일 작업에서 커서 대비 약 5.5배 적은 토큰을 사용하면서도 더 빠르게 작업을 완료하고 오류도 적었다.
IDE 비종속성: 터미널 기반이므로 기존 개발 환경(IntelliJ, VS Code, WebStorm 등)을 바꿀 필요 없이 터미널만 있으면 어디서든 실행 가능하다.
자동화에 강력: GitHub Action에 연결하여 풀 리퀘스트 시 자동 코드 리뷰를 하거나, 이슈 등록 시 코드를 작성하여 풀 리퀘스트를 만드는 등의 자동화가 가능하다.
원격 서버 사용 가능: GUI가 필요 없기 때문에 원격 서버에 접속한 상태에서도 바로 사용할 수 있다.
2.4. 최종 요약: AI 시대의 개발 본질
클로드 코드의 강력한 이점: 컨텍스트 엔지니어링과 네이티브 통합을 통해 필요한 정보만 정확하게 제공하고 강력한 퍼포먼스의 결과를 만들어낸다.
핵심 정리 3가지
AI 모델(엔진)과 AI 코딩 도구(자동차)를 구분해야 하며, 같은 모델이라도 도구에 따라 경험이 달라진다.
AI 모델 성능 향상으로 개발 도구 패러다임이 코드 편집기에서 터미널 기반으로 전환되고 있으며, 개발자의 역할은 실행자에서 설계자로 바뀌고 있다.
클로드 코드는 컨텍스트 엔지니어링과 네이티브 통합으로 같은 모델을 쓰더라도 완전히 다른 수준의 결과를 만들어낸다.
AI 시대의 개발 본질은 모델과 도구를 구분하고, 트렌드를 읽고, 컨텍스트의 중요성을 이해하는 것이며, 이는 AI 네이티브 개발자가 되어가는 과정이다.

기원전 287년, 시칠리아 시라쿠사.
아르키메데스는 포물선 아래의 넓이를 구하고 싶었다. 오늘날 우리가 ∫x² dx 라고 쓰는 것. 하지만 적분은커녕 좌표계조차 없던 시대다. 대수학도 없다. 문자 변수도 없다. 그가 가진 건 오직 삼각형과 비례뿐이었다.
그래서 그는 "소진법(Method of Exhaustion)"을 썼다. 포물선 안에 삼각형 하나를 넣는다. 남은 빈 공간에 또 삼각형 둘을 넣는다. 그 빈 공간에 또 넷을 넣는다. 매번 새 삼각형의 넓이는 이전의 1/4. 이걸 무한히 반복하면:
1 + 1/4 + 1/16 + 1/64 + ⋯ = 4/3
포물선 넓이 = 같은 밑변·높이 삼각형의 4/3배.
그는 이 무한급수의 합까지 순수 기하학으로 증명했다. 정사각형을 1/4씩 쪼개는 그림으로. 오늘날 적분으로 30초면 끝나는 계산을, 그는 24개의 명제에 걸쳐 증명했다. 천재의 증명이었다. 그리고 이 증명은 오직 포물선에만 작동했다.

1629년, 프랑스 툴루즈.
피에르 드 페르마는 낮에는 법관이었고, 밤에는 수학자였다. 그는 "최댓값을 찾는 법"을 발견했다. 놀라운 것은 이 방법이 오늘날의 미분과 거의 동일하다는 점이다.
f(x)의 최댓값을 찾고 싶다.
① f(x)와 f(x+e)를 "대략 같다(adequal)"고 놓는다
② 같은 항을 소거한다
③ e로 나눈다
④ e=0을 대입한다
이것이 우리가 배우는 f'(x)=0 풀기와 정확히 같은 절차다.
페르마는 이 방법을 접선 구하기에도 확장했다. 곡선 위의 한 점에서 접선의 기울기를 구하는 것 — 오늘날 도함수의 정의 그 자체다. 뉴턴은 훗날 "나의 미적분 아이디어는 페르마의 접선법에서 직접 왔다"고 인정했다.
하지만 페르마는 자기가 뭘 만들었는지 몰랐다. 그는 개별 문제를 풀었을 뿐, "미분"이라는 일반 체계를 만든 게 아니었다. 데카르트는 페르마의 방법이 논리적으로 부당하다고 공격했다. e를 0이 아니라고 하면서 나누고, 다시 0이라고 대입하는 게 모순이라는 것이다. (이 모순은 200년 뒤 코시의 극한 개념으로 해결된다.)

미적분학의 기본정리 (Fundamental Theorem of Calculus):
d/dx [∫₀ˣ f(t) dt] = f(x)
넓이를 구하는 연산(적분)을 미분하면 원래 함수가 돌아온다. 기울기를 구하는 연산(미분)의 반대가 넓이를 구하는 연산(적분)이다.
이건 마치 "곱하기의 반대가 나누기"라는 것을 발견한 것과 같다. 곱셈과 나눗셈이 별개의 연산이 아니라 하나의 동전의 양면이라는 것. 이걸 발견하기 전에는 곱셈 문제와 나눗셈 문제를 각각 따로 풀어야 했다. 발견한 뒤에는 하나를 알면 다른 하나가 자동으로 따라온다.
아르키메데스의 넓이 구하기(적분)와 페르마의 접선 구하기(미분)가 사실 같은 것의 앞뒤였다는 것. 이 연결 하나로, 흩어져 있던 2,000년의 수학이 하나의 체계로 통합되었다.
